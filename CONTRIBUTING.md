# Contributing to MirrorTab

First off, thank you for considering contributing to MirrorTab. It's people like you that make MirrorTab a great remote interaction tool.

## Where do I go from here?

If you've noticed a bug or have a feature request, make one! It's generally best if you get confirmation of your bug or approval for your feature request via [GitHub Issues](https://github.com/KostaD02/MirrorTab/issues) before starting to code.

## Project structure

```
src/
├── background/
│   ├── index.ts            # Service worker entry: wires session + tab listeners
│   ├── message-router.ts   # Routes chrome.runtime messages to SessionManager
│   └── session-manager.ts  # Class managing the full session lifecycle
│
├── content/
│   ├── main.ts             # Content script entry: bootstraps capture, replay, badge
│   ├── frame-bridge.ts     # Links the content scripts of a tab's frames (frame paths, cursor relay)
│   ├── mirror.ts           # EventCapture (source) + EventReplay (target) classes
│   └── role-badge.ts       # Floating SOURCE / TARGET badge injected into the page
│
├── popup/
│   ├── index.html          # Popup markup
│   ├── main.ts             # Mounts PopupController
│   ├── controller.ts       # All popup UI logic and message dispatch
│   ├── validate-url.ts     # URL validation helper
│   └── style.css           # Popup styles
│
├── replay/
│   ├── index.html          # Replay page markup
│   ├── main.ts             # Mounts ReplayPageController
│   ├── controller.ts       # File parsing, playback orchestration and DOM updates
│   └── style.css           # Replay UI styles
│
└── shared/
    ├── consts/             # APP_NAME, STORAGE_KEY, retry config
    ├── types/              # TypeScript interfaces and enums
    └── util/               # Pure utility functions (selector, logger, i18n, tab helpers, …)
```

`_locales/<code>/messages.json` holds the UI text of each language, `en` being the default.

`examples/` sits next to `src/` with the pages used for manual testing.

## Setting up for local development

**Requirements:** Node.js 18+, pnpm

```bash
# 1. Clone the repository
git clone https://github.com/KostaD02/MirrorTab.git
cd MirrorTab

# 2. Install dependencies
pnpm install

# 3. Start the dev server
pnpm start
```

Then load the unpacked extension in Chrome:

1. Open `chrome://extensions`
2. Enable **Developer mode** (top-right toggle)
3. Click **Load unpacked**
4. Select the `dist/` folder generated by the dev server

The extension hot-reloads on file changes while `pnpm start` is running.

## Trying it on the example pages

`examples/` holds static pages built for manual testing: plain form controls (`basic.html`), iframes with a nested frame and a cross-origin switch (`iframe.html`), and the hard cases such as custom dropdowns, dialogs, tabs and dynamic content (`advanced.html`). Content scripts only run on `http` and `https` pages, so open them through a local static server rather than from `file://`, and start a session with the same page as both the source and the target. Every page keeps an activity table of the events it received, so the two tabs can be compared side by side.

## Linting and Testing

We use formatting and linting rules to keep the codebase clean. Please ensure your code passes our CI checks before submitting a PR.

- To run the linter manually:
  ```bash
  pnpm lint
  ```
- To run tests (Jest):
  ```bash
  pnpm test
  ```
  _(Or `pnpm test:watch` for watch mode)_

## Translations

All user-facing text lives in `_locales/<code>/messages.json` and reaches the UI through `chrome.i18n`: `data-i18n` attributes in the HTML pages (`data-i18n-html` for markup, `data-i18n-attr` for attributes) and `t()` / `plural()` from `src/shared/util` in TypeScript. English is the default locale and the only file with `description` fields, which tell translators where a string appears.

To add or fix a language:

1. Copy `_locales/en/messages.json` to `_locales/<code>/messages.json`, using one of Chrome's [supported locale codes](https://developer.chrome.com/docs/extensions/reference/api/i18n#locales).
2. Translate the `message` values. Keep the `$PLACEHOLDER$` tokens and the `<strong>` markup as they are, and keep `appName` within 45 and `appDescription` within 132 characters, the limits Chrome puts on the manifest.
3. Messages that count things come in plural forms (`replayEventsLoaded_one`, `replayEventsLoaded_other`). Provide every form your language uses according to the [CLDR plural rules](https://cldr.unicode.org/index/cldr-spec/plural-rules): `other` is always required, Polish or Russian also need `few` and `many`, Arabic needs all six.
4. Run `pnpm i18n:report`. It prints the coverage table, writes `tmp/i18n-report.md` and fails on missing plural forms, stray placeholders or markup that differs from English. CI runs the same script on every pull request and keeps the table in a sticky comment.
5. Load the unpacked build with `chrome --lang=<code>`, or switch the browser language, to see the result in place. `pnpm test` also checks every locale against English.

Right-to-left languages (Arabic, Hebrew, Persian) flip the layout through `dir="rtl"` on the document, set from Chrome's `@@bidi_dir` message with a fallback on the UI language. `@kostad/brand` mirrors its components from that attribute on its own, so no RTL rules live in this repository; prefer logical properties (`margin-inline-start`, `padding-inline-end`) in any CSS added here.

## Pull Requests

1. Create a new branch from `main` for your feature or bugfix.
2. Commit your changes. We use `commitlint` and `husky` to enforce [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/). Please format your commit messages accordingly (e.g., `feat: added new tracking capability`, `fix: resolved UI bug`).
3. Push to your fork and submit a Pull Request against our `main` branch.
4. Provide a clear and descriptive PR body detailing what the PR solves or implements.
